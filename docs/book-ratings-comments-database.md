# Book ratings and comments: Prisma database integration

Owner: Rene Rodriguez. Runtime: Node.js 24, Express 5, Prisma 6.19.3.

## API contract

| Method and path | Input | Success |
| --- | --- | --- |
| POST /books/:bookId/ratings | JSON with userId and integer rating from 1 through 5 | 201, empty body |
| GET /books/:bookId/ratings/average | Book ID in the URL | 200, JSON number; null for an unrated existing book |
| POST /books/:bookId/comments | JSON with userId and nonempty comment text | 201, empty body |
| GET /books/:bookId/comments | Book ID in the URL | 200, JSON array, oldest first; [] when empty |

Both POST operations require existing Book and User IDs. The API trims IDs and
comment text. Missing/invalid input produces 400; nonexistent referenced records
produce 404. A URL with a missing book path segment does not match the route.
Unknown database errors produce a generic 500 response without connection details.
Record IDs and createdAt timestamps are generated by Prisma/the database. Supplied
client IDs or timestamps are ignored. Comment responses expose only comment fields,
not user credentials or credit-card information.

Each accepted rating POST appends a record, including repeat submissions by the
same user for the same book. This preserves the prototype's provisional policy.
Confirm the final repeat-rating policy with the Product Owner. An existing book
with no ratings returns null; a nonexistent book now returns 404.

## Files

- src/ratings/routes.js validates requests and sends responses.
- src/ratings/repository.js checks references and uses Prisma CRUD/aggregation.
- src/ratings/store.js is an isolated in-memory test double, not production storage.
- prisma/schema.prisma defines Rating, Comment, and their Book/User relations.
- prisma/migrations/20261026221500_add_ratings_comments/migration.sql adds only
  Rating and Comment, their indexes, constraints, and RLS settings.
- scripts/apply-ratings-comments-db.js verifies the team's migration history
  before invoking Prisma migrate deploy.

The migration enables RLS on the two new tables and removes direct anon and
authenticated grants. Express uses the server-side PostgreSQL connection already
configured locally. This does not implement Supabase Auth or Express authentication.
The two missing WishlistItem reverse relation fields are also supplied in Prisma
when that model exists; these fields do not create a WishlistItem database table.

## Installation and migration

1. Stop the local server. Install the supplied files using Install-RatingsComments.cjs.
   It validates existing feature files, preserves other schema models and .env,
   and backs up changed local files outside the repository.
2. Run npm.cmd install, npm.cmd run prisma:generate, and npm.cmd test.
3. Review the Rating/Comment SQL migration, then run npm.cmd run ratings:db.
   This command first reads table names and migration history. It stops without
   changes if other team migrations are pending, a failed migration is unresolved,
   or a feature table already exists without the expected migration history.
   Coordinate any such state with the migration owner; do not replace this step
   with migrate reset or db push against the shared database.
4. Run npm.cmd start. The start script loads the local .env explicitly.

The migration does not add the missing WishlistItem database table. That is the
wishlist owner's separate migration task. Do not assume it exists from the model.

## Local acceptance demonstration

Use a real Book.id and User.id from the shared project, not the old book-1/user-1
placeholders. IDs can be copied in Supabase Table Editor. If no user exists, create
a test account through POST /users and obtain its ID in Table Editor.

In a second PowerShell terminal, replace the two placeholders below:

```powershell
$bookId = 'PASTE_EXISTING_BOOK_ID'
$userId = 'PASTE_EXISTING_USER_ID'
$baseUrl = "http://127.0.0.1:3000/books/$bookId"

$first = @{ userId = $userId; rating = 5 } | ConvertTo-Json
$second = @{ userId = $userId; rating = 3 } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$baseUrl/ratings" -ContentType 'application/json' -Body $first
Invoke-RestMethod -Method Post -Uri "$baseUrl/ratings" -ContentType 'application/json' -Body $second
Invoke-RestMethod -Uri "$baseUrl/ratings/average"

$comment = @{ userId = $userId; comment = 'Helpful explanations and examples.' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$baseUrl/comments" -ContentType 'application/json' -Body $comment
Invoke-RestMethod -Uri "$baseUrl/comments" | ConvertTo-Json -Depth 5
```

If the selected book had no previous ratings, the average is 4. Existing ratings
also count; repeat demonstrations append additional records. Stop the API with
Ctrl+C, start it again, and repeat only the GET commands. The previously saved
average and comment must remain available. Inspect Rating and Comment in Supabase
to verify server-generated timestamps and correct references. Actual shared-database
verification must be recorded after running these checks locally.

## Verification boundaries and remaining integration

Automated HTTP tests explicitly use isolated stores or Prisma substitutes and do
not write to shared Supabase. Additional SQL validation is performed separately
against an isolated PostgreSQL engine. These checks do not establish that the
migration has been applied to the team's database.

Authentication, purchased-book eligibility, and the final repeat-rating policy
still need team decisions/integration. A caller-supplied userId is not proof of
identity or purchase. This increment does not implement a purchase/order system
and does not claim to satisfy purchase verification. Keep the database password
only in local/server configuration; it is never part of the source package.
